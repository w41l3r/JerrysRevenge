# Validation

Jerry's Revenge `0.4.0` is covered by unit and loopback integration tests for:

- CLI parsing and the no-traffic execution gate;
- Tomcat fingerprinting, Manager detection, and semicolon path variants;
- bundled and operator-supplied credential candidates, company-derived
  candidates, brute-force stopping behavior, and credential handoff;
- Manager HTML session/CSRF handling, multipart static-WAR upload, canary
  verification, cleanup, and strict custom-WAR validation;
- report redaction, restricted credential storage, and redirect suppression;
- CVE-2020-1938 version-range assessment, Ghostcat path validation, AJP13
  request attributes and response framing, response caps, fail-closed evidence
  handling, and mode-`0600` raw evidence.

Run the local checks from the repository root:

```bash
GOCACHE=/tmp/jerrysrevenge-go-cache go test -count=1 ./...
GOCACHE=/tmp/jerrysrevenge-go-cache go test -race -count=1 ./...
GOCACHE=/tmp/jerrysrevenge-go-cache go vet ./...
GOCACHE=/tmp/jerrysrevenge-go-cache go build -buildvcs=false -trimpath -o bin/jerrysrevenge ./cmd/jerrysrevenge
```

The final local validation on 2026-09-23 completed successfully with Go
`1.24.9` on Linux/amd64. The built `bin/jerrysrevenge` artifact identified
itself as `0.4.0` and had SHA-256:

```text
86e851238ec60beed494bb99449c7c0514204f6eaff8d6b6e51c147cd53c96e6
```

## Ghostcat Docker homologation

The bounded Ghostcat workflow was also validated with a `0.4.0` development
artifact (SHA-256
`6928ab2ff4c9105a4363b3ac5a67f5f73dfa62307783f9c4e342a4de5e3b522a`)
against the historical official image used by the project's loopback-only lab:

```text
image:  tomcat:8.0-jre8
digest: sha256:268403c3fa09afd9310ced7e83ac021927dca0f04a394a80a0b0220f62e056ed
server: Apache Tomcat/8.0.53
HTTP:   127.0.0.1:18080 -> container 8080
AJP:    127.0.0.1:18009 -> container 8009
```

The initial invocation omitted `--execute`. Tomcat's access log remained empty,
confirming that planning mode sent neither HTTP nor AJP traffic. The authorized
active run then produced exactly five access-log entries: four HTTP discovery
requests and one AJP-backed `GET /asdf` generated by the forged servlet include
attributes. There were no retries.

The AJP response was status `200`, content type `application/xml`, and 1,232
bytes. The restricted response file and the container's
`ROOT/WEB-INF/web.xml` had the same SHA-256:

```text
bdcc11a6ef959b5ac4b01791393a61907cc30a25d80e492c7bf74e41c7c5d9cd
```

The evidence directory was mode `0700`; the acquired file was mode `0600`.
Only metadata and the digest appeared in terminal and sanitized report output.
The exact ephemeral container was stopped and removed after validation, and
both loopback ports were confirmed closed. The reusable Compose definition in
[`lab/ghostcat/compose.yaml`](../lab/ghostcat/compose.yaml) also passed
`docker compose config` validation.

After that single authorized acquisition, evidence-directory and AJP-host
preflight checks were moved earlier so invalid local inputs fail before any
HTTP or AJP traffic. The protocol request/response implementation did not
change. The final artifact hash shown above passed normal, race-enabled, and
fail-closed loopback tests, but was not used for a second Docker file read
because the approved active batch was limited to one acquisition.

Tomcat 8.0.x was already end-of-life and is not explicitly included in the
Apache advisory's authoritative version ranges, so the offline range check
correctly remained `UNVERIFIED`. The separately authorized behavioral test
nevertheless `CONFIRMED` the file-read primitive in this specific lab image.

## Safety invariants

The deployment workflow enforces these invariants:

- it accepts only a canonical one-file static `index.html` canary WAR;
- it rejects JSP, classes, JARs, JavaScript, extra archive entries, symlinks,
  and traversal paths;
- it requires an authenticated Manager HTML page, session cookie, and valid
  CSRF nonce before upload;
- it attempts immediate undeployment after a successful upload, including
  after marker-verification failure;
- it records cleanup failure and the random context path for manual review.

The Ghostcat workflow enforces these invariants:

- version applicability is assessed locally on every completed discovery run;
- file access requires the separate `--ghostcat --execute` gate;
- the plan fixes the exact AJP endpoint and selected resource;
- each target receives at most one AJP request and no automatic retry;
- URLs, literal or percent-encoded traversal, path parameters, queries,
  fragments, backslashes, controls, and empty path segments are rejected before
  traffic;
- non-default response bodies are preserved but their exact file identity is
  classified `INFERRED` until operator review;
- an unsafe evidence destination is rejected before HTTP or AJP traffic;
- response bytes are capped at 1 MiB and are never printed or copied into the
  sanitized runbook;
- JSP evaluation, command execution, callbacks, persistence, upload, and bulk
  file collection are not implemented.

Active target validation requires explicit action-specific authorization and
`--execute`. Engagement-specific commands, targets, credentials, and raw
evidence belong under the gitignored `reports/` and `restricted/` directories
and are intentionally excluded from public documentation.
